1
Puerta 1
Bases de
datos
La que casi nadie cierra
Por default, tu tabla es pública
✕ El problema, en concreto
Creas la tabla en Supabase, Claude la conecta, todo funciona. Pero sin configurar nada más, cualquiera puede abrir las herramientas de desarrollador de su navegador, copiar la URL de tu proyecto y pegarle /rest/v1/usuarios directo — sin loguearse, ve la tabla completa. Hay bots que rastrean el internet buscando exactamente esa URL.
✓
La corrección: Row Level Security (RLS) activado en cada tabla — cada una decide quién puede leer y quién puede escribir. Sin sesión válida, no hay acceso a nada.
El prompt para esta puerta
Pégalo cuando conectes o audites una base de datos
"Revisa todas mis tablas en Supabase y dime cuáles tienen Row Level Security desactivado. Actívalo en todas. Después crea las políticas necesarias para que cada usuario autenticado solo pueda leer y escribir sus propios datos — nadie más, ni siquiera otro usuario logueado."
RLS no se activa solo — hay que pedirlo por su nombre, no asumir que "conectar la base de datos" ya lo incluyó.
2
Puerta 2
API keys
La que se copia con un clic
Si el navegador la lee, un desconocido también
✕ El problema, en concreto
Publicas la landing. Alguien abre "Ver código fuente" o la pestaña Sources de las herramientas de desarrollador, busca la palabra "key" y la encuentra en texto plano dentro del JavaScript que se manda al navegador. La usa desde su propia cuenta — el cargo llega a la tuya.
✓
La corrección: la key vive solo en el servidor, en una variable de entorno que el navegador nunca recibe. Todo lo que la necesita pasa primero por tu backend.
El prompt para esta puerta
Pégalo antes de publicar cualquier proyecto con Next.js
"Revisa mi proyecto y dime qué variables de entorno con datos sensibles — API keys, tokens, contraseñas de servicio — quedan expuestas al navegador. En Next.js, eso es cualquier variable con el prefijo NEXT_PUBLIC_, o cualquier key usada directo en un componente cliente. Muévelas a rutas de servidor (API routes) y confírmame que ninguna llega al bundle del navegador."
La palabra clave es NEXT_PUBLIC_: ese prefijo significa literalmente "mándala al navegador". Ninguna key sensible debería llevarlo.
3
Puerta 3
Límite de
peticiones
La que evita el cheque en blanco
Un endpoint sin límite es una cuenta abierta
✕ El problema, en concreto
Tu formulario de contacto dispara un correo o una llamada a una API de pago por cada envío. Un bot descubre la URL del endpoint y lo llama miles de veces en una hora — tu proveedor te suspende la cuenta, o el cargo por uso te llega multiplicado por mil.
✓
La corrección: un límite de peticiones (rate limit) por IP o por usuario — diez intentos por minuto, no diez mil — más verificación humana en lo público.
El prompt para esta puerta
Pégalo en cualquier endpoint o formulario público
"Agrega límite de peticiones (rate limiting) a todos mis endpoints públicos: máximo X peticiones por minuto por IP. Si alguien pasa el límite, responde con error 429 en vez de ejecutar la acción. Si es un formulario público, agrega también verificación tipo captcha."
No es paranoia: una API de pago sin límite es tu tarjeta con el número abierto. Pide el límite antes de publicar, no después del cargo.
4
Puerta 4
Contraseñas
Lo interno no es "secreto por URL"
"Nadie va a encontrar esa URL" no es seguridad
✕ El problema, en concreto
Compartes por WhatsApp el link de tu dashboard de ventas "para que lo vea el equipo". Ese chat se reenvía, o alguien lo copia a un grupo más grande, y ahora cualquiera con el link ve tus números — sin haber iniciado sesión nunca, porque la página nunca la pidió.
✓
La corrección: contraseña verificada del lado del servidor antes de mostrar cualquier dato. Si la verificación falla, la página no carga la información — no basta con ocultarla en pantalla.
El prompt para esta puerta
Pégalo en cualquier dashboard o panel interno
"Este panel es interno. Agrega verificación de contraseña del lado del servidor: si la contraseña no es correcta, la página no debe cargar ningún dato, ni siquiera en el HTML inicial. No lo resuelvas solo ocultando el contenido con CSS o JavaScript del lado del cliente."
La diferencia importa: verificar en el servidor significa que los datos nunca salen si la contraseña falla — no que solo se esconden con estilos.
